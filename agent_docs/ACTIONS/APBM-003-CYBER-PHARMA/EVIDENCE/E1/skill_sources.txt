1: # stark-recon
2: 
3: > **An Agent Skill for the Stark Industries App Factory.** Establishes ground truth about a repo before any Architect authors a brief or FFM against it.
4: 
5: ## What it does
6: 
7: Docs drift. Handbooks, APP_BRIEFs, and session logs make claims about disk state that go stale. An Architect who authors against a stale doc produces a correct artifact built on wrong data — and pays for it later in conflict after conflict at the build gate.
8: 
9: `stark-recon` closes that hole. The Engineer (Claudy) runs it against the actual filesystem + grep + build output and produces a **Recon Report**. The Architect authors only from that report. Where any doc and the filesystem disagree, the filesystem wins.
10: 
11: This is **Recon Mode** — the Architect's equivalent of Plan Mode. Plan Mode keeps the Engineer from coding blind; Recon Mode keeps the Architect from authoring blind.
12: 
13: ## Mandatory-first
14: 
15: **No brief, no FFM, gets authored without a Recon Report for the repo's current state.** Every project, every kit, every phase. Re-run when significant work has landed since the last recon.
16: 
17: ## How to run
18: 
19: Drop this folder under your `_SKILLS/`. Then point the agent at it:
20: 
21: > "Go read `_SKILLS/stark-recon/CLAUDE.md` and run a recon on this repo. Read-only. Hand me the report when done."
22: 
23: The agent reads `CLAUDE.md` (doctrine) → `SKILL.md` (methodology) → executes `templates/RECON_MISSION.md` → answers in `templates/RECON_REPORT_TEMPLATE.md` format → STOPS and hands back the report.
24: 
25: ## What it is NOT
26: 
27: Not `brain-drain`. Brain-drain is a deep architecture extraction (11 docs, hours). Recon is fast, targeted doc-vs-disk verification (one report, ~30 min) focused only on drift that would mislead authoring.

28: ## The Recon Sequence
29: 
30: Six phases. Read-only throughout. Announce the scope, execute, assemble one report, STOP.
31: 
32: ### Phase 0 — Day-0 Ground-Truth Sweep (run FIRST)
33: 
34: The highest-value drift, caught fastest. Per `RECON_MISSION.md` Section 0:
35: - Verify **every handbook-named file exists** on disk (the #1 lie class).
36: - Verify **handbook-claimed exports/shapes** match disk (`cat` the stores/utils the handbook describes; compare).
37: - Run the **forbidden-zone greps** against the kit itself, NOW (`: any`, `dangerouslySetInnerHTML`, `user_metadata.(is_|role)`).
38: - Verify **every doc-named route/path** by `find` before trusting it.
39: - Confirm the **test runner** (`grep -E '"test":|vitest|jest' package.json`).
40: - Ground-truth **env names** from the example file + `grep process.env` in code — never from docs.
41: - Run the **build route table** (`npm run build` output) — ground truth for what surfaces exist.
42: 
43: Every finding gets a label. Every doc-vs-disk mismatch gets flagged.
44: 
45: ### Phase 1 — Stack & Structure
46: 
47: `RECON_MISSION.md` Sections 1-2: exact versions from `package.json` (Next, React, TS, Tailwind → token mechanic, Node pin, test runner, other heavyweights); kit structure vs handbook claims; existing directories (`src/services/`, `src/utils/`, `src/store/`, `src/types/`); route groups; `proxy.ts` vs `middleware.ts`.

7: ## Identity / Mission
8: 
9: `stark-recon` is an **Agent Skill** in the Stark Industries App Factory. Its job: **establish ground truth about a repo before any Architect authors a brief or an FFM against it.**
10: 
11: The skill exists because of one hard-won lesson: **docs lie.** Starter-kit handbooks, APP_BRIEFs, and prior session logs make claims about disk state that drift out of true. An Architect who authors against a stale doc produces a *correct artifact built on wrong data* — and the cost surfaces later as conflict after conflict at the Engineer's build gate.
12: 
13: `stark-recon` closes that hole. The Engineer (Claudy) runs it against the actual filesystem + grep + build output and produces a **Recon Report**. The Architect authors only from that report. **Where any doc and the filesystem disagree, the filesystem wins — every time.**
14: 
15: This is the **Recon Mode** protocol — the Architect's equivalent of Plan Mode. Plan Mode keeps the Engineer from coding blind. Recon Mode keeps the Architect from authoring blind. Together they ground all three roles (Operator, Architect, Engineer) against one verified source of truth.

19: ## MANDATORY-FIRST (Non-Negotiable Doctrine)
20: 
21: **No brief and no FFM may be authored for a repo until a `stark-recon` Recon Report exists for that repo's current state.**
22: 
23: - The Architect is **forbidden** from authoring `APP_BRIEF`, `DATA_CONTRACT`, `UI_SPEC`, `_project/CLAUDE.md`, or any FFM file without a Recon Report in hand.
24: - This applies to **every project, every kit, every phase** — not just the first.
25: - A Recon Report goes stale. If significant work has landed since the last recon (a phase closed, a kit upgraded, branches merged), **re-run recon** before authoring the next brief/FFM.
26: - The Operator may explicitly override (with acknowledgment) for trivial cases — but the default is: recon first, always.
27: 
28: If an Architect starts authoring without a report, that is a process violation. Surface it and run recon first.

32: ## Skill Type & Activation
33: 
34: - **Type:** Agent Skill (the agent executes autonomously; the operator does not paste each command).
35: - **Invocation:** manual. Operator points the agent at this folder: *"Go read `_SKILLS/stark-recon/CLAUDE.md` and run a recon."*
36: - **Execution:** read-only **of the inspected codebase**. The agent greps, reads files, runs the build, and assembles the report. **It makes NO changes to source, NO fixes, NO git operations, NO `cd && git`.** The ONE write it makes is the report file itself (see Output Contract below) — that is the deliverable, not a mutation of the code under inspection.
37: - **Plan Mode:** compressed. Because the inspection is read-only and low-risk, the agent does NOT gate on each command. It announces the recon scope, executes the sweep + sections, and writes the report.
38: - **The one checkpoint:** the agent writes the report **to a file**, then STOPS and hands the Architect the file path. The Architect reviews the file before authoring. That handoff is the mandatory gate.

61: ## Doctrine — Always In Effect
62: 
63: 1. **Disk wins.** Where any doc and the filesystem disagree, the filesystem is truth. Flag every drift.
64: 2. **Evidence discipline.** Every finding is labeled EVIDENCE / INFERENCE / CLAIM / GAP / QUESTION (see `references/EVIDENCE_DISCIPLINE.md`). The Architect must be able to tell what was verified vs guessed.
65: 3. **Read-only of the inspected codebase.** No mutations to source. The recon observes; it never fixes. Defects found are *reported*, not patched — fixing is a separate authorized pass. (This does NOT forbid writing the report file — that's the deliverable; see rule 7.)
66: 4. **Ground-truth the Day-0 sweep first.** Section 0 of the mission (verify handbook-named files exist, run the forbidden-zone greps, confirm the route table) runs before everything else. It catches the highest-value drift fastest.
67: 5. **The Surprises section is the gold.** The open-ended sweep is where the NEXT unknown lesson gets found. Never skip it.
68: 6. **One pass, one report.** Answer the whole mission, hand back one structured report. Don't trickle findings.
69: 7. **OUTPUT CONTRACT — the report MUST be written to a file.** Never produce the recon on-screen only. The full report is written to:
70:    ```
71:    agent_docs/recon/RECON_<project>_<phase>_<YYYY-MM-DD>.md
72:    ```
73:    (Create `agent_docs/recon/` if it doesn't exist.) On-screen, the agent prints only a SHORT confirmation + the file path + a 3-5 line headline summary. The full report lives in the file so the Architect can read, diff, and keep it. A recon that exists only in chat scrollback is a failed recon — it can't be referenced, version-tracked, or handed off cleanly.

FILE: agent_docs/SKILLS/stark-recon-skill-v1.1/references/ANTI_PATTERNS.md
1: # ANTI-PATTERNS — stark-recon
2: 
3: Recon-specific failure modes. Each is a way a recon can betray its purpose.
4: 
5: ---
6: 
7: ### AP-1 — Trusting a doc claim without verifying on disk
8: 
9: **The cardinal sin.** The handbook says `app-role.ts` exists, so the recon writes "app-role.ts exists" without running `ls`. This is the exact failure the skill was built to prevent. **Every doc claim is a CLAIM until disk confirms it.** If you didn't run the command, you didn't verify it.
10: 
11: ### AP-2 — Fixing defects during recon
12: 
13: The recon finds `user: any` and "helpfully" types it. NO. Recon is read-only **of the inspected codebase**. It REPORTS the defect with a label and a recommendation; a separate authorized pass fixes it. (Writing the report FILE is not a "fix" — it's the deliverable. The prohibition is on mutating the code under inspection.)
14: 
15: ### AP-10 — Producing the report on-screen only (the file-output failure)
16: 
17: The recon assembles a beautiful report and prints it to chat — but never writes it to a file. **This is a failed recon.** A report that lives only in chat scrollback can't be referenced later, can't be diffed against the next recon, can't be version-tracked, and forces the Operator to copy-paste it around. The full report MUST be written to `agent_docs/recon/RECON_<project>_<phase>_<YYYY-MM-DD>.md`. On-screen gets only a short confirmation + the path + a 3-5 line headline. This anti-pattern is why v1.1 made file-output an explicit Output Contract — early runs went to screen because "read-only" was misread as "write nothing at all." Read-only protects the *inspected code*; the report file is the deliverable.
18: 
19: ### AP-3 — Skipping the Surprises section
20: 
21: The mission's open-ended sweep feels optional because it has no fixed checklist. It is the OPPOSITE of optional — it's where the next unknown lesson lives (the orphan files, the unimported primitive with `as any`, the stale-doc fossil). The known questions catch known drift; the Surprises section catches what no one thought to ask.
22: 
23: ### AP-4 — Unlabeled findings
24: 
25: A report that states facts without EVIDENCE/INFERENCE/CLAIM/GAP/QUESTION labels forces the Architect to guess what was verified. That reintroduces exactly the blind-authoring risk recon exists to remove. Label everything.
26: 
27: ### AP-5 — Mutating anything / running git
28: 
29: `cd && git show` can trigger repo hooks. Any write changes the snapshot. Recon observes only: read, grep, build (build is read-only of source). No writes, no git, no hooks.
30: 
31: ### AP-6 — Trickling findings instead of one assembled report
32: 
33: Reporting section-by-section as you go, in fragments, forces the Architect to reassemble. Run the whole mission, assemble ONE structured report in the template format, hand it off once.
34: 
35: ### AP-7 — Treating recon as brain-drain
36: 
37: Brain-drain is a deep architecture extraction — 11 evidence docs, hours, full system map. Recon is fast, targeted doc-vs-disk verification — one report, ~30 min, focused only on drift that would mislead authoring. Don't write 11 docs. Don't map every function. Answer the mission and stop.
38: 
39: ### AP-8 — Stale recon treated as current
40: 
41: A Recon Report is a snapshot. If a phase closed, a kit was upgraded, or branches merged since the report, it's stale — re-run before authoring. Authoring against a stale recon is the same failure as authoring against a stale handbook, one level up.
42: 
43: ### AP-9 — Letting seeded examples read as requirements
44: 
45: The mission's seeded examples (the QR fossil, the `app-role.ts` lie, etc.) are ILLUSTRATIONS of drift classes from a past run, not requirements for the current repo. Replace them with what THIS repo shows. A recon that reports a past project's findings as if they were the current repo's is worse than no recon.

FILE: agent_docs/SKILLS/stark-recon-skill-v1.1/references/EVIDENCE_DISCIPLINE.md
1: # EVIDENCE DISCIPLINE
2: 
3: > Every finding in a Recon Report carries one of five labels. Without labels, the Architect can't tell what was verified from what was guessed — and authoring against a guess is the exact failure this skill prevents.
4: 
5: ---
6: 
7: ## The Five Labels
8: 
9: - **EVIDENCE** — directly found on disk, with a citation (file path + line, or the exact command + its output). The strongest claim. *"`useAuthStore.user` is typed `SupabaseUser | null` — EVIDENCE: src/store/useAuthStore.ts:12."*
10: 
11: - **INFERENCE** — a reasonable conclusion drawn from observed structure, with the basis stated. *"The kit gets away with the server-only AppRole import because every value-level usage is in a server component — INFERENCE from grep of import sites."*
12: 
13: - **CLAIM** — a doc or the operator says it; NOT independently verified. Always flag claims for verification. *"Handbook says the kit uses Vitest — CLAIM; see EVIDENCE below where package.json shows Jest."*
14: 
15: - **GAP** — an expected thing was not found. State what was expected and where you searched. *"No `src/middleware.ts` — GAP (expected per pre-Next-16 convention); `src/proxy.ts` present instead, which is correct for Next 16."*
16: 
17: - **QUESTION** — needs operator clarification; phrased as an explicit question. *"`DashboardCard.tsx` has zero consumers — QUESTION: delete as orphan, or keep as a Phase-2 starter pattern?"*
18: 
19: ---
20: 
21: ## The Governing Rule: Disk Wins
22: 
23: When any doc (handbook, APP_BRIEF, prior session log) and the filesystem disagree, **the filesystem is truth.** The doc gets flagged as drift; the report records reality.
24: 
25: This is non-negotiable. The entire reason `stark-recon` exists is that docs drift out of true and Architects author against them. Recon's job is to surface every such drift so the Architect authors from disk, not from a stale claim.
26: 
27: ## Read-Only
28: 
29: Recon **reports** drift; it never **fixes** it. Finding a defect (a `: any`, an orphan file, a stale env name) means logging it with a label and a recommendation — not patching it. Fixing is a separate, explicitly-authorized pass (a cleanup cluster or an FFM build), never part of recon. The recon must leave the repo byte-for-byte unchanged and run zero git operations.
30: 
31: ## Citation Style
32: 
33: - File facts: `path:line` (`src/utils/app-role.ts:1`).
34: - Command facts: the command + the salient output (`grep -E '"test":' package.json → "test": "jest"`).
35: - Absence facts: the command that found nothing (`find src/app -type d -name "(superadmin)" → no results`).
36: 
37: A finding the Architect can't trace to a citation is not EVIDENCE — downgrade it to INFERENCE or CLAIM and say so.
