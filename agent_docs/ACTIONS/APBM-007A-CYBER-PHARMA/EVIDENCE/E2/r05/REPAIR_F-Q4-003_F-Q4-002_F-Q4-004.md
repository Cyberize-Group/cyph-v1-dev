## 1. F-Q4-003 — paid new owner not provisioned (AC-016 / AC-017)

### Evidence

| Source | Fact |
|---|---|
| QA `live-results.json` | Operation `25acbfb9…` ends `attention` / `not_paid`, with `owner_user_id` set, `owner_was_existing = true` and no account or store. Three payment events for it (`checkout.session.completed`, `customer.subscription.created`, `invoice.paid`), all with event IDs from the same second, are `processed` with 0 attempts. One `access_link` notification is `sent`, 1 attempt |
| QA `provider-readback.json` | Session complete and paid, 8910 USD cents; subscription active; invoice paid 8910 |
| `0057` `operation_lease` | Grants the lease when it is free, expired, **or `lease_owner = p_owner`** |
| `provisioning.ts` at `c638f79` | `WORKER` is one constant per server process. Every webhook delivery and status poll handled by the `next start` process passes the same owner, so they all hold "the" lease at once |
| `0058` `provision_paid_registration` | Returns `not_paid` when the operation's status is anything but `paid` or `provisioning` |
| `resolveOwner` at `c638f79` | Decides from the operation loaded at the start of the run. Its only write of `owner_was_existing = true` without a signed-in match is: address found, purchaser not signed in as it → `attention` / `owner_signin_required` / `owner_was_existing = true`, written without any condition |

### Confirmed cause

The DEV row can only be produced by overlapping runs, in this order:

1. Run A creates the identity and records `owner_user_id` with `owner_was_existing = false`, then writes `provisioning`.
2. Run B holds the same lease, because the owner string is the same, and loaded the operation before A recorded the owner. It finds A's identity by address and, not seeing it as its own, writes `attention` / `owner_signin_required` / `owner_was_existing = true`. That write lands after A's `provisioning` write.
3. A's `provision_paid_registration` sees `attention` and returns `not_paid`, which A records.

A run made after A had finished would have resumed the recorded owner and provisioned. Every later run then repeats the reclassification, because the flag now says "existing".

**Reproduced from the code alone:**
- **Unit model:** the candidate ends `attention` for both runs.
- **Real SCRATCH SQL:** the candidate ends `attention` / `not_paid`, `owner_was_existing = true`, with this operation's identity as owner, 0 accounts and the access link sent once. That is the DEV row exactly (`scratch/scratch_r05_candidate_control.json`).

The schedule is fixed by hooks so the result does not depend on timing; two earlier control attempts are preserved. Under the same shared lease, four concurrent advances make **four** `createUser` calls in the unit model.

**Inference, not observed:** the precise DEV schedule. No server log of the two runs exists in the evidence. The conclusion rests on the code and the end state, which admit no other path.

### Repair (`src/server/provisioning.ts`, +88 −31)

| Requirement | Change |
|---|---|
| One provisioning outcome under concurrency | **One lease owner per call** (`pp-<uuid>`), not per process. A competing call waits up to 8 s for the holder (polling every 250 ms), then sees its outcome: provisioned, or `busy` if the holder is still working |
| Stale or losing workers cannot overwrite | **Fenced writes:** every write to the operation during a run requires `lease_owner = <this call>`. A call that lost its lease stops, writes nothing and returns `busy`. The lease is renewed before the identity step and with the `provisioning` write |
| An identity this operation created is never reclassified | **Provenance:** new identities are created with `app_metadata.apbm_operation = <operation>` (server-set, not user-editable). An identity found by address is this operation's when it carries that marker. An identity created before the marker existed counts only if all three hold: it is the identity this operation recorded, it was created after the operation began, and the purchaser was not signed in at checkout. A create that fails because the address already exists accepts the found identity only on the same test (before, it was accepted unconditionally) |
| Existing-owner protection | Any other identity, including one created by another operation or one that existed before this operation, still goes to `owner_signin_required` and is attached only after sign-in (`resumeForUser`, unchanged) |
| Payment truth | Every run re-reads Stripe and moves `attention` back to `paid` before continuing. Failures stay recoverable (tested) |
| No duplicate identity or provisioning | One create per operation (marker plus lease); `provision_paid_registration` is exactly once (`already_provisioned`) |

`checkout.ts` adds `created_at` to the operation row it reads, which the provenance rule uses.

## 2. F-Q4-004 — access email failed with 429 (diagnosis, then repair)

### Evidence

| Source | Fact |
|---|---|
| QA `live-results.json` | OWNER_2's operation `d1c76239…` (existing identity, signed out, paid) is `attention` / `owner_signin_required`. Its `access_link` notification is `failed`, 1 attempt, `last_error_code = "429"`. Three payment events for it, all in the same second, are processed |
| `provisioning.ts` / `accessEmail.ts` at `c638f79` | `last_error_code` is written only from the result of `sendSignInLink`, which calls Supabase Auth `signInWithOtp` with the publishable key and stores the error **status**. So "429" is the HTTP status the Supabase Auth API returned to the portal's `/auth/v1/otp` request |
| App limiter | `rateLimit` in `http.ts` answers inbound requests with `slow_down` and never writes a notification. **Not the source** |
| Code at `c638f79` | In the `owner_signin_required` branch every advance calls `ensureAccessNotification`. With the row `pending` and 0 attempts, each concurrent caller sends, then writes `attempts = 0 + 1` (read-then-write). The last writer's result replaces the others |

### Diagnosis

| Stage | Classification |
|---|---|
| Failing service | Supabase Auth, the `/auth/v1/otp` request from `signInWithOtp` (evidence: code path and stored status) |
| Mail provider | Not reached by the refused request. GoTrue's own limits answer 429; a provider (SMTP) failure is reported by GoTrue as 500. This last point is knowledge of GoTrue, not evidence from this run |
| Most probable cause (product-caused) | The same concurrency as F-Q4-003. Three events in one second, under a shared lease, each asked Auth for a link to the same address. Auth's per-address interval refused the later request with 429, and its "failed, 1 attempt" write replaced the earlier send's result |
| Reproduction | Unit model and real SCRATCH control on the candidate both give mailer results `ok, 429` and a final row `failed` / `429`. With the repair: one send, row `sent` |

**Remaining gap, stated precisely:**
- **Single attempt or duplicate?** The evidence cannot prove a second request existed in DEV, or that the first was accepted. The stored value holds the status only; Auth and mail logs were not read (no live Auth calls in scope); and no inbox was checked.
- **Which limit?** A project-wide email limit returns 429 too and cannot be excluded from the stored evidence.
- **Improvement:** the repair now stores Auth's error code with the status (for example `429:over_email_send_rate_limit`). The message, which distinguishes the per-address interval from a project limit, is still not stored; the Auth logs remain the authority.

### Repair (product-caused part)

- **Exclusive per-call lease** (§1): advances of one operation no longer overlap, so they no longer send concurrently.
- **Claim before sending:** `ensureAccessNotification` claims the attempt with a compare-and-set on `attempts` before calling the mailer. Only the caller whose claim lands sends, and its result is written against that attempt number. This also covers a resend that races a poll.
- **Kept:** the durable failed state; the existing 60-second resend interval; at most one access notification per operation (`dedupe_key`).
- **Error detail:** `accessEmail.ts` keeps Auth's error code with the status.

### Retry disposition (unchanged; nothing invented)

There is no timed or background retry. A `failed` access notification is retried only when `ensureAccessNotification` runs again more than 60 s after the last attempt:
- **User-driven:** the status page's reconcile poll, and the resend button (`resendAccessEmail`, which forces a resend at most once a minute).
- **Operator-driven:** `operator-reconcile.mjs --operation <id>`.
- **Provider-driven:** a webhook redelivery.

For OWNER_2's operation the same paths apply. Running any of them sends a live email, which is a Director or QA decision. Nothing was run.

## 3. F-Q4-002 — stale Checkout after a draft edit (AC-009)

### Evidence

QA `checkout-promotion-edit-same.json`:
- the operation is still `checkout_open` at draft revision 1, total 9900;
- the current draft is at revision 2, quoted 8910, with `consent_revision` NULL;
- the same-key retry returned the old Checkout.

### Cause

In `startCheckout` at `c638f79`, a same-key retry always resumed the open operation. The r04 rule settled a stale attempt only on a **different** key, and only on a revision change; a re-quote at the same revision, which clears consent, was not seen as stale at all. This was r04 limitation L5.

### Repair (`src/server/checkout.ts`, +42 −15)

| Requirement | Change |
|---|---|
| No retry under any key returns an earlier attempt's Checkout | An open attempt is resumed only while it **still describes the draft**: same revision; consent recorded for that revision; same quoted total, promotion code and price. Otherwise it is settled first, whatever the key |
| Settled safely | **Recorded session:** read it. **Unknown outcome:** its own keys return what Stripe created (r04 `sessionFor`). An open session is **expired through Stripe**, and the operation is released only on that proof (`expired`, unpaid). A **paid** session is never released or replaced (`operation_in_progress`) and goes on to provisioning |
| Current quote and consent enforced | The new attempt goes through the normal path: current quote, `holdNpi`, consent recorded for the current revision from the request (all three consents required before any provider call) |
| The browser's key keeps working | The settled operation keeps the browser's key, so the new attempt is stored under a **successor key** (`<key>_n<first 8 hex of the settled operation>`), which the same browser key still resumes |
| One intended customer | The new attempt reuses the earlier attempt's customer |
| F-Q4-001 preserved | An unchanged checkout after a lost answer still resumes the original operation, with one customer, one session and one operation (tested) |
